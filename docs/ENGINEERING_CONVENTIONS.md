# Engineering conventions

Persistent rules for everyone working on this repository, including future development
sessions. Read this file and `PROJECT_STATUS.md` before starting work.

## Roles and scope

* **Director / Product Owner**: the repository owner. Owns product vision, final decisions
  and scope approval.
* **Co-Director**: roadmap, architecture review, engineering briefs, milestone review.
* **Technical Lead**: implementation, technical decisions inside an approved brief, testing,
  integration and technical documentation.

Work only within the scope of an approved engineering brief. Do not start a new milestone
without a new brief. Do not change the product vision.

## Repository, authorship and attribution

* Commit with the repository owner's existing Git identity. Never change global Git settings
  and never invent an identity.
* No AI, assistant or tool attribution anywhere: no co-author trailers, "generated by"
  banners, assistant signatures, or assistant-specific configuration files in the repository.
* Commit messages are neutral and descriptive, in Conventional Commits style
  (`feat(vision): ...`, `fix(camera): ...`, `test: ...`, `docs: ...`, `build: ...`, `perf: ...`).
* Keep legally required copyright notices and third-party attribution (see
  `docs/THIRD_PARTY_NOTICES.md`). Do not fabricate authorship statements.
* Never commit credentials, `.env` files, webcam recordings or screenshots, personal data,
  machine-specific paths, downloaded models or test assets. Gesture calibration recordings
  (`recordings/`, landmark numbers of a real person's hands) stay local. Check `git status` and the diff
  before every commit.
* Never force-push, rewrite published history or delete user files.
* Do not publish stable releases or tags unless a brief explicitly asks for it.

## Milestones and checkpoints

Statuses: `NOT_STARTED`, `IN_PROGRESS`, `COMPLETED`, `FAILED`, `BLOCKED`.

For every checkpoint: inspect, implement, write meaningful tests, run them, fix root
causes, verify integration with earlier work, document results in `PROJECT_STATUS.md` and
the milestone report, and commit the verified work in logically scoped commits.

A checkpoint is `COMPLETED` only when its acceptance criteria are met and backed by
evidence. Hardware criteria that could not be exercised are `BLOCKED` with a manual
checklist, never reported as passed. After each group of milestones run a full integration
audit of the whole codebase and record it in `docs/audits/`.

## Quality rules

* Never declare incomplete work complete, never fabricate or round up test results, never
  hide failures, warnings or limitations.
* Never weaken a test to make it pass. Change a test only when the test itself is wrong, and
  say why in the commit message.
* No placeholders or mock implementations in production code. Test doubles live in `tests/`.
* Do not swallow exceptions to hide problems. Worker threads log unexpected exceptions with
  tracebacks and surface a user-readable state.
* No unnecessary dependencies or speculative abstractions.
* Every displayed metric must come from real measured state. No invented confidence values.
* Every fixed defect gets a regression test in `tests/regression/`.

## Code conventions

* Python 3.12, type annotations everywhere, `from __future__ import annotations`.
* Formatting and linting: `ruff format` and `ruff check` (configuration in `pyproject.toml`,
  line length 100). Both must pass before committing.
* Layering rules in `docs/architecture/ARCHITECTURE.md` are enforced by
  `tests/unit/test_architecture.py`. MediaPipe is imported only in `vision/hand_tracker.py`.
* Timestamps are `perf_counter_ns` integers. Landmarks are normalized coordinates of the
  unmirrored frame; mirroring is display-only.
* Record consequential decisions in `docs/architecture/DECISIONS.md`.

## Testing

* `tests/unit`: fast, isolated. `tests/integration`: several modules together, the real model on
  still images, the UI via pytest-qt (offscreen). `tests/regression`: one test per fixed defect.
  `tests/hardware`: physical webcam; run with `--hardware`.
* CI (GitHub Actions, Windows) runs format, lint and all hardware-independent tests. It does
  not and cannot validate the webcam. Live verification is done locally and recorded.
* Performance claims require measurements from `scripts/benchmark_pipeline.py` or
  `scripts/stability_session.py`, recorded with the test environment.

## Privacy

All processing is local. No frames are uploaded, recorded or stored. The application never
opens a camera without a user action. No telemetry. Do not add network access to the
application beyond the one-time, user-initiated model download.
